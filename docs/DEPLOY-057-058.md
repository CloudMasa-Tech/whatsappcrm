# Deploying this release to a new production machine

Covers everything added in this cycle — email campaigns with lead flow,
the Facebook Page integration, origin isolation for the in-frame
proxies, and the role-authorization fixes — and how to point the app at
a **different Supabase project** (new URL + anon key).

Read [`DEPLOYMENT.md`](../DEPLOYMENT.md) first for the base install.
This document only covers what is new or changed.

---

## 0. The one thing that catches people out

`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are
**compiled into the browser bundle at build time**, not read at runtime.

Changing which Supabase project the app talks to therefore requires a
**rebuild**, not a restart. The same applies to
`NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_APP_LOCALE` and
`NEXT_PUBLIC_SANDBOX_ORIGIN`.

```bash
# Wrong — the old project's URL is still baked into the JS
docker compose restart web

# Right
docker compose build --no-cache web && docker compose up -d web
```

Symptom of getting this wrong: the server talks to the new database
while the browser still talks to the old one, so login appears to work
but data is missing, or you get `Invalid API key` in the console.

## 1. Apply the database migrations

Two new migrations: `057_email_lead_flow.sql` and
`058_facebook_config.sql`.

### On an existing database (001–056 already applied)

```bash
# 1. Read-only check that the DB is ready. Every row should say OK.
psql "$DATABASE_URL" -f supabase/preflight_057_058.sql

# 2. Apply both migrations in one pass.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/apply_057_058.sql

# 3. Re-run the preflight — the POST-APPLY section should now be all OK.
psql "$DATABASE_URL" -f supabase/preflight_057_058.sql
```

Or paste `supabase/apply_057_058.sql` into the Supabase SQL Editor.
**Note:** the Editor wraps the whole script in one transaction, so a
single error rolls everything back and looks like nothing happened.
Scroll up to find the *first* error.

Every statement is idempotent. Re-running is safe and is the supported
way to recover from a partial apply.

### On a brand-new Supabase project

Apply every migration in order:

```bash
for f in supabase/migrations/*.sql; do
  echo "--- $f"
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f" || break
done
```

Verified: all 58 migrations apply cleanly to an empty database, and
re-running the whole set is a no-op.

Two fixes in this release matter only for fresh databases, because an
existing one already has the objects:

| File | Fix |
|---|---|
| `001_initial_schema.sql` | 16 columns had `DEFAULT extensions.extensions.uuid_generate_v4()`. The doubled qualifier parses as *database*`.`*schema*`.`*function*, so Postgres rejects it with "cross-database references are not implemented" and the migration aborts. |
| `051_qr_realtime_publication.sql` → `054_…` | Two files shared the `051` prefix. The CLI keys `schema_migrations` on that number, so the second insert violated the primary key and aborted the run. |
| `049_allowed_channels.sql` | `ADD CONSTRAINT` had no existence guard, so re-running the migration failed with "constraint already exists". Now wrapped in a `DO` block. |

### After applying, in the Supabase dashboard

**Database → Replication → `supabase_realtime`**: confirm
`whatsapp_sessions` is enabled. Migration 054 tries to add it and emits
a `WARNING` (not an error) if it cannot. Without it the QR pairing
screen falls back to polling.

## 2. Environment variables

### Changed / new in this release

| Variable | Required? | Notes |
|---|---|---|
| `NEXT_PUBLIC_SANDBOX_ORIGIN` | Recommended | Second hostname resolving to the **same** deployment, e.g. `https://sandbox.crm.example.com`. Isolates the Facebook/Instagram in-frame proxies so framed Meta scripts cannot read the Supabase session. Unset = old same-origin behaviour, and the hubs show a warning banner. **Build-time.** |
| `EMAIL_INBOUND_SECRET` | If using email replies | Shared secret the provider presents to `/api/email/inbound`. `openssl rand -hex 24`. The route **fails closed** — with neither this nor `MAILGUN_SIGNING_KEY`, every inbound request is rejected. |
| `MAILGUN_SIGNING_KEY` | Optional | Mailgun HMAC verification instead of the shared secret. |
| `META_APP_SECRET` | If using Facebook/Instagram | Verifies `X-Hub-Signature-256` on the Facebook webhook. Can also be stored per-project via the Connect panel, which takes precedence. |
| `SMTP_*` | If sending email | Unchanged, but now also read by campaign sending. A per-project row in `email_configs` takes precedence over these. |

### Pointing at a different Supabase project

```bash
NEXT_PUBLIC_SUPABASE_URL=https://<new-ref>.supabase.co   # build-time
NEXT_PUBLIC_SUPABASE_ANON_KEY=<new anon key>             # build-time
SUPABASE_SERVICE_ROLE_KEY=<new service role key>         # runtime, secret
```

`ENCRYPTION_KEY` is **not** interchangeable between deployments. It
decrypts every stored Meta access token, Facebook Page token and QR
session credential. Moving to a new Supabase project without carrying
the same key forward makes all of those undecryptable, and every
channel must be reconnected. Back it up separately from the database.

If you are standing up a genuinely new environment (not migrating
data), generate fresh secrets:

```bash
openssl rand -hex 32   # ENCRYPTION_KEY
openssl rand -hex 32   # GATEWAY_API_TOKEN
openssl rand -hex 32   # GATEWAY_SIGNING_SECRET
openssl rand -hex 32   # GATEWAY_WEBHOOK_SECRET
openssl rand -hex 24   # EMAIL_INBOUND_SECRET
```

## 3. Build and start

```bash
cp .env.example .env        # then fill it in
docker compose build --no-cache web
docker compose up -d
docker compose ps           # web + gateway should be healthy
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000   # → 200 or 307
```

## 4. Create the first super admin

Migration 047 promotes the **earliest** profile by `created_at` to
`super_admin`. On a fresh database, sign up first — that account becomes
the platform operator. To promote someone later:

```sql
UPDATE profiles SET platform_role = 'super_admin' WHERE email = 'you@example.com';
```

This must be done in SQL. Migration 048 installs a trigger that blocks
`platform_role` changes made as the `authenticated` role, specifically
to stop users self-promoting through the REST API.

## 5. Per-channel setup

### Email campaigns

1. **Settings → Email** (admin only) or `SMTP_*` env vars.
2. Outbound and open/click tracking work immediately.
3. For **replies** to land in the inbox, point a provider's inbound
   parse at:
   `https://<your-domain>/api/email/inbound?secret=$EMAIL_INBOUND_SECRET`
   and add the MX records the provider specifies.

Tracking links are built from `NEXT_PUBLIC_SITE_URL` — if it is wrong,
pixels and click-throughs point at the wrong host and silently record
nothing.

### Facebook

1. **/facebook → Connect Page**, paste a **Page** access token (not a
   User token). It is verified against the Graph API before being
   stored encrypted.
2. In Meta for Developers, subscribe the Page to `messages` and
   `messaging_postbacks` with callback
   `https://<your-domain>/api/facebook/webhook` and the verify token
   shown in the Connect panel.
3. Store the app secret so `X-Hub-Signature-256` verification passes.
4. `pages_messaging` requires App Review before it works for anyone
   outside your test users.

## 6. Verify

```bash
# Migrations
psql "$DATABASE_URL" -f supabase/preflight_057_058.sql   # all OK

# Auth guards — an agent must NOT be able to write channel config
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<domain>/api/admin/users     # 401/403
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<domain>/api/email/inbound   # 401 (fails closed)

# Tracking pixel returns a GIF even for an unknown token
curl -s -o /dev/null -w '%{content_type}\n' https://<domain>/api/email/track/open/deadbeefdeadbeefdeadbeefdeadbeef
```

In the app: the inbox status strip should list every unconfigured
channel, and `/admin` should redirect non-super-admins to `/dashboard`.

## 7. Rollback

The migrations are additive — new tables and columns, no drops or type
changes — so the previous application build runs unchanged against the
new schema. To roll back, redeploy the old image. No SQL down-migration
is needed, and running one would destroy campaign engagement history.
